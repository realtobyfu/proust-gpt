How a Proust Passage Gets to the Screen

A step-by-step walkthrough of React data flow, using our actual code

Chapter 1

The Big Picture

When you type a question and hit enter, here's what happens at a very high level:

You type a question │ ▼ Backend: searches Pinecone, finds passages, sends them over HTTP │ ▼ Hook: useStreamingQuery receives the data, stores it in React state │ ▼ ChatPage: reads from state, passes data down as props │ ├──▶ PassageCard (the collapsed card in the chat) └──▶ ReaderPanel (the side panel on desktop)

The key question is: at which step does the passage text go from full-length to truncated?

React Concept: State and Props

State is data that a component owns and can change. When state changes, React re-renders that component.

Props are data passed from a parent to a child. The child can read them but can't change them.

Think of it like a chain of post offices. State is the letter being written at one office. Props are copies of that letter forwarded to the next office down the line. If the original letter is wrong, every copy downstream is also wrong.

Chapter 2

The Backend Prepares the Data

The backend does three things in sequence:

retrieve_passages() — searches Pinecone (30 candidates), reranks with Cohere (keeps top 5), stitches adjacent passages together. Returns full text — could be thousands of characters.
retrieval.py:322
_format_passages() — converts internal Document objects into plain dictionaries: {book, chapter, text, text_fr, volume, index}. Still full text here.
retrieval.py:302
Branching point! — the server decides which streaming function to use.
server.py:243

This branching point is the crux of the issue. Let's look at the server code:

// server.py — the /api/explore_lost_time/stream endpoint

if needs_agent(query, history):          # complex or follow-up query?
    return StreamingResponse(
        async_sse_generator(stream_agent_response, ...)   # ← PATH B
    )

return StreamingResponse(
    async_sse_generator(stream_rag_response, ...)       # ← PATH A
)

Path A: stream_rag_response

Simple, first-time queries. Yields each passage directly:

for p in passages:
    yield {"type": "sources",
           "passages": [p]}
# ↑ Full text! No truncation.

Path B: stream_agent_response

Complex/follow-up queries. Wraps each passage in _preview_passage():

return [{"type": "sources",
  "passages": [_preview_passage(p)]}
  for p in unique]
# ↑ Truncated to 200 chars!

So what does _preview_passage do? It's simple — it chops the text:

def _preview_passage(p: dict) -> dict:
    preview = dict(p)                      # shallow copy
    for key in ("text", "text_fr"):
        val = preview.get(key, "")
        if len(val) > 200:
            preview[key] = val[:200] + "…"    # chop + ellipsis
            preview["_truncated"] = True       # flag it
    return preview
Imagine you're sending a book by mail. Path A sends the whole book. Path B rips out page 1, writes "..." at the bottom, sticks a Post-It note on it saying "_truncated: true", and sends only that. The idea is: the recipient can request the full book later if they want it.
Chapter 3

SSE Transport — Just a Pipe

Server-Sent Events (SSE) is the protocol used to stream data from backend to frontend. For our purposes it's just a pipe — it doesn't modify the passage text at all. It:

  1. JSON-serializes the dict: json.dumps(data)
  2. Splits long payloads across multiple data: lines (for proxy safety)
  3. Sends keepalive comments every 15 seconds

Whatever text the backend put in the dict — full or truncated — goes through unchanged.

Chapter 4

The React Hook Receives the Data

Now we're in the browser. The useStreamingQuery custom hook is responsible for receiving the SSE stream and turning it into React state that components can use.

React Concept: Custom Hooks

A hook is a function that starts with use and lets you "hook into" React features like state. A custom hook bundles together related state and logic so components don't have to deal with the messy details.

useStreamingQuery encapsulates all the SSE connection, parsing, and state management. Components just call query("madeleine memory", "explore") and read passages and response.

Here's the relevant part — what happens when a "sources" event arrives:

// useStreamingQuery.ts — inside processSSEBlock()

case 'sources':
  if (event.passages) {
    setPassages(prev => {
      const updated = [...prev, ...event.passages!];
      passagesRef.current = updated;
      return updated;
    });
  }
  break;

React Concept: useState and the Updater Pattern

setPassages(prev => [...]) is the "updater function" form of useState. Instead of saying "set passages to X", you say "take the previous value and compute the new value from it."

Why? Because SSE events arrive one at a time. Each event adds one passage. If we wrote setPassages([...passages, ...event.passages]), we'd use a stale passages value (a closure over an old render). The updater ensures we always build on the latest state.

The critical thing here: the hook stores exactly what the backend sent. It doesn't modify the text. If Path B truncated it, the hook stores truncated text. If Path A sent full text, the hook stores full text.

After all events arrive, the hook's state looks like:

// What the hook's state contains:
passages = [
  {
    book: "Swann's Way",
    chapter: "Overture",
    text: "For a long time I used to go to bed early. Sometimes, when I had put out my candle, my eyes would close so quickly that I had not even time to say «I'm going to sleep.» And half …",  // ← 200 chars + "…" (from agent path)
    _truncated: true,              // ← the flag
    index: 42,
  },
  // ... more passages
]
Chapter 5

ChatPage — The Middleman

ChatPage is the main page component. It calls the hook and stores the results in its own state to build a chat history. Then it passes passages down to child components via props.

// ChatPage.tsx — state for the reader panel

const [selectedPassage, setSelectedPassage] = useState<Passage | null>(null);
const [selectedPassageGroup, setSelectedPassageGroup] = useState<Passage[]>([]);

// When user clicks a passage card on desktop:
const handleSelectPassageForReader = (passage, allPassages) => {
  setSelectedPassage(passage);          // ← same object from the hook
  setSelectedPassageGroup(allPassages);
};

React Concept: Props Drilling

Data flows one way in React: parent → child. ChatPage passes the passage object as a prop to both PassageCard and ReaderPanel. This is sometimes called "props drilling" — data drilling down through layers.

The key insight: it's the same JavaScript object. ChatPage doesn't copy or modify it. Whatever the hook stored (full or truncated), that exact object reaches the child components.

So ChatPage renders both components with the same data:

// Simplified ChatPage render

// The card in the chat stream:
<PassageCard
  passages={displayPassages}        // ← from hook state
  onSelectPassage={(p) => handleSelectPassageForReader(p, displayPassages)}
/>

// The side panel (desktop only):
<ReaderPanel
  passage={selectedPassage}          // ← same object that was clicked
  allPassages={selectedPassageGroup}
/>
Chapter 6

The Two Components — Where the Bug Lives

Both components receive the same (possibly truncated) passage. The question is: does each component know how to fetch the full text?

PassageCard (works correctly)

Has three pieces of logic that work together:

  1. State: fullTexts — a cache of fetched texts
  2. Function: fetchFullText(index) — calls the API
  3. Effect: when expanded + truncated → auto-fetch
  4. Display: full?.text ?? passage.text

ReaderPanel (had the bug)

Was missing all of that! Just did:

  1. No fullTexts state
  2. No fetchFullText function
  3. No effect to trigger the fetch
  4. Display: passage.text directly

Let's look at the PassageCard's working logic in detail:

React Concept: useEffect

useEffect lets you run code after a render, in response to some data changing. You give it a function and a list of dependencies:

useEffect(() => { /* do something */ }, [dep1, dep2])

React watches the dependencies. When any of them changes, it runs the function again. It's how you say: "whenever X changes, do Y."

// PassageCard.tsx — the working pattern

// 1. State to cache fetched full texts
const [fullTexts, setFullTexts] = useState<Record<number, {text, text_fr?}>>({});

// 2. Function to fetch from the backend
const fetchFullText = async (passageIndex) => {
  const res = await fetch(`/api/read/passage_text?index=${passageIndex}&lang=both`);
  const data = await res.json();
  setFullTexts(prev => ({...prev, [passageIndex]: data}));
};

// 3. Effect: "when this card expands AND text is truncated → fetch"
useEffect(() => {
  if (expanded && passage.index != null && isTruncated(passage)) {
    fetchFullText(passage.index);
  }
}, [expanded, passage]);

// 4. Display: prefer full text, fall back to truncated preview
const full = passage.index != null ? fullTexts[passage.index] : undefined;
const enText = full?.text ?? passage.text;   // ← "use full if available, else preview"

React Concept: The ?? Operator (Nullish Coalescing)

full?.text ?? passage.text means: "if full exists AND has a text property, use it. Otherwise, use passage.text."

This is the fallback chain: try the good data first, fall back to whatever we have.

ReaderPanel was just doing displayText = passage.text — with no fallback to a lazy-loaded full version. Since the passage object from the hook still has the 200-char truncated text (from the agent path), that's all the panel ever showed.

Chapter 7

The Complete Journey, Traced End to End

Let's follow one passage from backend to screen, for a complex query that uses the agent path:

Pinecone returns a passage with 2,000 characters of Proust text.
_format_passages() puts it in a dict: {text: "For a long time I used to go... [2000 chars]", index: 42, ...}
_preview_passage() chops it: {text: "For a long time... [200 chars]…", _truncated: true, index: 42}
SSE pipe sends the JSON. No changes.
useStreamingQuery parses it, stores in passages state. Still 200 chars.
ChatPage receives passages from hook. Passes the same objects to children.
PassageCard — user clicks to expand → useEffect fires → fetches /api/read/passage_text?index=42&lang=both → gets full 2,000 chars → displays full text.
ReaderPanel — user clicks card on desktop → panel opens → displays passage.text directly → only shows 200 chars + "…". Never fetches the full text.
Chapter 8

The Fix

The fix adds the same three ingredients to ReaderPanel that PassageCard already had:

// ReaderPanel.tsx — added code

// 1. State for caching full texts
const [fullTexts, setFullTexts] = useState({});

// 2. Fetch function
const fetchFullText = async (index) => { ... };

// 3. Effect: auto-fetch when panel opens with truncated text
useEffect(() => {
  if (passage && passage.index != null && isTruncated(passage)) {
    fetchFullText(passage.index);
  }
}, [passage]);  // ← runs whenever a new passage is selected

// 4. Display: prefer full text
const full = passage.index != null ? fullTexts[passage.index] : undefined;
const enText = full?.text ?? passage.text;

React Concept: Why [passage] as the Dependency?

In the PassageCard, the dependency is [expanded, passage] — it fetches when the card is expanded. But the ReaderPanel is always expanded (it's a side panel). So the trigger is just [passage] — "whenever a different passage is selected, check if it's truncated and fetch if needed."

Chapter 9

Why Only Sometimes? The needs_agent() Split

One more important detail: you won't always see this bug. It only happens when your query goes through the agent path.

needs_agent(query, history) returns true for:

  • Follow-up questions (when there's conversation history)
  • Complex multi-step queries

For a simple first query like "madeleine memory", it goes through Path A (stream_rag_response) which sends full text — no truncation, no bug, everything looks fine.

That's what makes this bug sneaky: it only appears in certain conditions, making it easy to miss during testing.
